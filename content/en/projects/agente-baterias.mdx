## Context and problem

Every day, a car battery store got the same question: "do you have a battery for my car?". The answer depends on four details (model, year, engine and transmission) and on a table that maps each vehicle to the right battery and price. ## Solution and architecture

Two parts that depend on each other.

**The agent** reads the customer's message, extracts model, year, engine and transmission, and queries, through an API, the database that maps vehicle, battery and price. The answer always comes from the database, never from the model's memory.

**The management system** is the dashboard where the store registers vehicles, batteries and prices. When the agent gets a vehicle that is not on file, it creates a draft entry and notifies the seller, who confirms the data in the dashboard. From then on, the agent can answer for that vehicle.

## Decisions and trade-offs

<Decision
  title="Data lives in the database, not in the prompt"
  tradeoff="The catalog has to be kept up to date, which is why the management dashboard is part of the project rather than an extra."
>
  Prices and compatibility change. With the table in the database, the agent never makes up a battery: it only answers what is on file, and the store updates everything without touching the agent.
</Decision>

<Decision
  title="An unknown vehicle becomes a draft entry, not a guess"
  tradeoff="The customer waits for the seller's confirmation instead of getting an instant answer."
>
  Getting the battery wrong costs a sale and the customer's trust. The agent would rather say it will confirm, and each confirmation makes the catalog more complete.
</Decision>

<Decision title="Access rules in the database (RLS)" tradeoff="More setup at the start of the project.">
  Permissions apply to every access path (the dashboard, the API or the agent) instead of relying on each screen to run the right check.
</Decision>
